# prompt.md: Sequential Feature Prompts

## How to use

1. Put `plan.md`, `plot.md`, `prompt.md` in the repo root. Copy `agent.md` to `CLAUDE.md`.
2. Give Claude **one prompt at a time**, in order. Each prompt starts with the same preamble.
3. Move to the next prompt only when the report says `Next: Ready for F<NN+1>`.
4. If a report says "Not ready", reply: `Fix the remaining issue in F<NN>, then report again.`

**Preamble (prepend to every prompt):**
```
Follow CLAUDE.md. Read plan.md and plot.md. Build ONLY the feature below, run its checks, then reply in the mandatory report format.
```

## Phase 1: Synthetic world

### F02 – Synthetic data generator (Profile A)
Implement `backend/data/generator.py` with `generate(profile="A", seed=SEED)`. It produces these tables:
- `employers`
- `employees`
- `payroll_runs` (scheduled vs actual pay date, status)
- `attendance` (earned days per month)
- `advance_requests`
- `advances` (amount, fee, outcome)
- `repayments` (by waterfall step)
- `resignations`

Cover 24 months, ~40 employers and ~6,000 employees. Inject the patterns from `plan.md` §7 (month-end and Eid surge, lateness persistence, short-tenure attrition, chronic borrowers, abusers). Losses must arise mechanically from events.

`backend/data/seed.py` writes `seed.db`. The app builds `seed.db` at startup if it is missing.

**Accept when:**
- same seed → identical row counts and checksums (test);
- generation finishes < 60s;
- a sanity test confirms the injected patterns exist (e.g. day-25+ request rate > day-5 rate, often-late employers have more late runs).

### F03 – Profile B (stress-test world) and data report
Add `profile="B"` with different parameters and noise (e.g. more late employers, different salary distribution, shifted surge timing). Write `docs/data_report.md`, auto-generated by a script: table sizes, key distributions, pattern checks for A and B. Keep Profile B data separate from training.

**Accept when:** the report generates from code; tests confirm that A ≠ B on the declared parameters.

## Phase 2: Core money mechanics

### F04 – Double-entry ledger
`app/ledger/`: accounts (`upay_pool`, `employee_wallet:<id>`, `employer:<id>`, `fees_income`, `loss_provision`) and journal entries with lines that sum to zero. Money is stored as integer paisa.

Functions: `post_entry`, `balance(account)`, `reconcile()`.

**Accept when:** tests cover a balanced entry, rejection of an unbalanced one, reconciliation after 1,000 random entries, and no float money anywhere.

### F05 – Session simulation state
Per-session sim DB (temp dir, keyed by `X-Session-Id`, TTL cleanup), initialised from `seed.db` plus the current sim date.

Endpoints:
- `POST /sim/reset`
- `GET /sim/state`
- `POST /sim/advance-time {days}`
- `POST /sim/jump-to-payday`

Moving time triggers scheduled payroll events for that session.

**Accept when:** two sessions are isolated (test); reset restores the initial state; the ledger reconciles after time jumps.

### F06 – Rule engine
`app/rules/`: eligibility (opted-in employer, tenure ≥ minimum, no open advance beyond the limit, cooling-off, kill switch), the hard cap `min(cap% × salary, earned_to_date − outstanding)`, fee calculation and repayment date. Each rule returns a machine-readable trace item.

**Accept when:** unit tests cover each rule including edge cases (day 1 earned = small, resigned employee, kill switch on, chronic borrower).

## Phase 3: ML models (train offline, commit artifacts)

**For every model in this phase:**
- **Training data:** a time-based split on Profile A, with the last 3 months held out for testing.
- **Leakage:** a test asserts that no feature uses data after the decision date.
- **Artifacts:** save `artifacts/<model>.joblib` and append metrics to `artifacts/metrics.json`.
- **Baseline:** compare against the baseline listed in `plan.md` §8.
- **Stress test:** also evaluate on Profile B.
- **Inference:** add a function in `app/ml/`.

### F07 – M1 Employer reliability
- **Target:** payroll late beyond grace next month.
- **Features:** lateness history (lags, rolling), industry, size, seasonality.
- **Model:** LightGBM + calibration.
- **Report:** PR-AUC, Brier, calibration bins vs the last-month baseline.
- **Inference:** `employer_risk(employer_id, as_of) -> {prob, top_reasons}` (SHAP).

**Accept when:** artifacts and metrics exist, the leakage test passes, and inference returns reasons.

### F08 – M2 Repayment-failure risk and tiering
- **Target:** advance not recovered by payday + grace.
- **Features:** tenure, salary band, past advance count and recovery, earned ratio, employer M1 probability as of the decision date, request amount ÷ salary.
- **Model:** LightGBM + calibration.
- **Tier mapping (A/B/C/D):** via config thresholds. The tier sets the share of the hard cap allowed (e.g. A 100%, B 70%, C 40%, D → human queue).
- **Policy comparison:** compare against the flat 20% cap on loss rate at equal approval.

**Accept when:** the metrics and policy-comparison numbers are written to `metrics.json` by code.

### F09 – M3 Attrition before payday
- **Target:** resigns before next payday.
- **Features:** tenure, recent attendance drop, salary band, employer industry, recent advance frequency.
- **Model:** LightGBM + calibration, plus SHAP reasons.
- **Tiering:** high attrition risk lowers the tier by one step (a rule in `app/rules/`, documented).

**Accept when:** metrics vs the tenure-rule baseline are saved; the tier adjustment test passes.

### F10 – M4 Capital need forecast
- **Target:** total advances outstanding next month (overall and per employer).
- **Model:** LightGBM quantile at α = 0.1, 0.5 and 0.9.
- **Features:** calendar (month, Eid flag), headcount, past request volume, employer mix.
- **Baselines:** previous month and seasonal naive.
- **Report:** MAE, pinball loss and P10–P90 coverage on test (A and B).
- **Inference:** `capital_forecast(months_ahead=3)` and `required_pool = P90 × (1 + buffer%)`.

**Accept when:** coverage is computed and saved; the forecast endpoint returns three months of bands.

### F11 – M5 Abuse / chronic-borrowing detection
- **Model:** Isolation Forest on behaviour features (frequency, max ratio usage, request timing patterns, rapid repeats), plus rules for chronic borrowing (consecutive months).
- **Evaluation:** precision@k on planted abusers and chronic borrowers.
- **Flags** feed cooling-off and the human queue.

**Accept when:** precision@k is saved; flagged cases route to the queue in tests.

## Phase 4: Decision and settlement services

### F12 – Decision service and explanations
`POST /advance/offer {employee_id, amount}`:
1. eligibility rules;
2. hard cap;
3. M1/M2/M3 → tier;
4. M5 flag;
5. offer `{max_amount, approved_amount, fee, repayment_date, tier, status: offered|queued|declined, reasons[]}`.

`reasons` merge the rule trace and the top SHAP features into **plain structured codes** (e.g. `EMPLOYER_ON_TIME`, `EARNED_DAYS_LIMIT`). Log every decision with its inputs and model versions.

**Accept when:** tests run the plot.md scenarios S1, S2 and S5 and produce the expected statuses.

### F13 – Advance acceptance, human queue, kill switch
- `POST /advance/accept` posts to the ledger: pool → wallet, plus the fee schedule.
- Ops endpoints:
  - `GET /ops/queue`
  - `POST /ops/queue/{id}/approve|reject {note}` (the note is required)
  - `POST /ops/kill-switch {on}`
- Rejections and approvals are logged with the analyst note.

**Accept when:** ledger reconciliation holds; a decision cannot be made without a note; the kill switch blocks new offers while existing advances still settle.

### F14 – Payday settlement and recovery waterfall
On payday (sim time):
1. Generate the employer deduction notice (one list, one total).
2. Simulate employer remittance according to employer behaviour (on time, late, partial, default).
3. Apply the waterfall: remittance → consented wallet auto-debit → carry-over (limit reduced) → write-off to `loss_provision` after grace.

Endpoints:
- `GET /employer/{id}/deduction-notice`
- `GET /employer/{id}/deduction-notice.csv`

**Accept when:** scenarios S1, S3 and S4 pass end-to-end in tests, and the ledger reconciles after each.

### F15 – Scenario triggers
`POST /sim/scenario {name}` for S1–S7 from plot.md. Each scenario sets up the needed state in the session (e.g. forces the employer default flag, Eid month, chronic history).

**Accept when:** one test per scenario asserts the expected system behaviour from the plot.md table.

## Phase 5: LLM layer

### F16 – Grounded explanation text
`app/llm/explain.py`: input = the structured decision JSON (reason codes, amounts, dates), output = 2–3 short sentences in EN and BN.
- Use the Anthropic API if `ANTHROPIC_API_KEY` is set; otherwise use a deterministic template per reason code.
- The system prompt forbids changing numbers or decisions.
- **Post-check:** every number in the output must match the input. If it does not, fall back to the template.

**Accept when:** the template works with no key; a test injects a malicious string into a field and confirms the output still only reflects the decision (or falls back); the number-match check is tested.
